# Agentic Dev Team Framework
### Portable infrastructure for research-to-implementation projects
**Author:** Watson Ndethi | April 2026  
**Drop into:** any project repo as `docs/agentic_dev_team_framework.md`  
**Runtime targets:** Hermes (primary), OpenClaw (fallback), Copilot (IDE)

---

## What this is

A reusable framework for running a managed AI dev team on any project
via Telegram. Drop this document and the accompanying config files
into a new repo, run the bootstrap message, and Hermes activates the
full team: PM, Senior Dev, Tester, Evaluator, Research Analyst, Writer,
and a Skill Generator that creates new roles on demand.

The framework includes:
- Universal repo entry points (AGENTS.md, .github/copilot-instructions.md)
- Six role SOUL.md / SKILL.md files optimised for Hermes
- OpenClaw fallback config for the same roles
- Commitizen-enforced Conventional Commits with changelog automation
- Structured PR templates with agent-readable review criteria
- GitHub Actions for commit linting and changelog generation
- A Skill Generator role that creates new SKILL.md files from task patterns
- Model provider recommendations per role with free-tier fallbacks

Everything is parameterised. Replace `{{PROJECT_NAME}}`,
`{{REPO_OWNER}}`, `{{REPO_NAME}}`, and `{{DOMAIN_CONTEXT}}` with
project-specific values before committing.

## Part 1: Commit discipline — Commitizen + Conventional Commits

<cite>Commitizen enforces Conventional Commits, enables automatic version
bumping, and generates CHANGELOG.md from commit history.</cite> Every agent
in the team writes commits in this format. Humans do too.

### Commit format

```
<type>(<scope>): <description>

[optional body — explain why, not what]

[optional footer]
Refs: #<issue-number>
Co-authored-by: Hermes Agent
```

### Types used in this framework

| Type | Triggers SemVer | Use for |
|------|----------------|---------|
| `feat` | MINOR bump | New script, module, or capability |
| `fix` | PATCH bump | Bug fix in existing code |
| `feat!` or `BREAKING CHANGE` | MAJOR bump | API or schema change |
| `docs` | none | Documentation changes |
| `test` | none | Test additions or changes |
| `refactor` | none | Code restructuring, no behaviour change |
| `perf` | none | Performance improvement |
| `chore` | none | Config, tooling, dependencies |
| `ci` | none | GitHub Actions, automation changes |
| `data` | none | Dataset changes (custom type for research projects) |
| `eval` | none | Evaluation results, metric changes (custom) |

### Scopes — define per project

Scopes go in parentheses after the type. For a research pipeline:

```
feat(pipeline): add Transphone batch processing
fix(eval): correct bootstrap CI calculation in TCPR
data(pairs): add 15 Armstrong-sourced minimal pairs
docs(design): clarify IPA encoding decision rationale
test(validator): add decomposed Unicode edge case
```

Define your project scopes in `.cz.toml` under `[tool.commitizen]`.

### Setup files

**`.cz.toml`** — drop in repo root:

```toml
[tool.commitizen]
name = "cz_conventional_commits"
version = "0.1.0"
version_files = [
    "pyproject.toml:version"
]
update_changelog_on_bump = true
changelog_incremental = true
tag_format = "v$version"

[tool.commitizen.customize]
schema_pattern = "(feat|fix|docs|test|refactor|perf|chore|ci|data|eval)(\\(\\S+\\))?!?:(\\s.*)"
```

**`.commitlintrc.json`** — validates every commit message:

```json
{
  "extends": ["@commitlint/config-conventional"],
  "rules": {
    "type-enum": [2, "always", [
      "feat", "fix", "docs", "test", "refactor",
      "perf", "chore", "ci", "data", "eval"
    ]],
    "scope-case": [2, "always", "lower-case"],
    "subject-case": [2, "always", "lower-case"],
    "header-max-length": [2, "always", 100],
    "body-leading-blank": [2, "always"],
    "footer-leading-blank": [1, "always"]
  }
}
```

**`.github/workflows/commitlint.yml`** — blocks PRs with bad commits:

```yaml
name: Commit Lint
on: [pull_request]
jobs:
  commitlint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: wagoid/commitlint-github-action@v6
        with:
          configFile: .commitlintrc.json
```

**`.github/workflows/changelog.yml`** — auto-generates CHANGELOG on merge:

```yaml
name: Changelog
on:
  push:
    branches: [main]
jobs:
  changelog:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          token: ${{ secrets.GITHUB_TOKEN }}
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install commitizen
      - run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          cz changelog --incremental
          git add CHANGELOG.md
          git diff --staged --quiet || git commit -m "chore(changelog): update for $(cz version -p)"
          git push
```

### Agent commit instruction

Every agent in the team produces commits in this format. Add this
to every SKILL.md and SOUL.md under a `## Commit discipline` section:

```
Commit format: <type>(<scope>): <description>

Rules:
- type: one of feat|fix|docs|test|refactor|perf|chore|ci|data|eval
- scope: lowercase noun describing the affected component
- description: imperative mood, lowercase, max 72 chars, no period
- body: explain WHY not WHAT, separated by blank line
- footer: always include Refs: #<issue-number> if a task issue exists
- breaking changes: append ! to type or add BREAKING CHANGE: footer
- never: past tense ("added"), vague descriptions ("misc updates"),
  missing type, or direct push to main
```

## Part 3: SOUL.md — Hermes project soul

SOUL.md is Hermes's persistent identity file for the project. It loads
at every session start and defines what Hermes knows about the project,
how it behaves, and what constraints it operates under. Unlike SKILL.md
files which define role behaviour, SOUL.md defines project-wide values.

Place this at the repo root as `SOUL.md`. Hermes detects it
automatically.

**`SOUL.md` template:**

```markdown
# {{PROJECT_NAME}} — Project Soul

## Identity
You are the orchestrating agent for {{PROJECT_NAME}}.
Repo: github.com/{{REPO_OWNER}}/{{REPO_NAME}}
Lead researcher: {{RESEARCHER_NAME}}

## Project purpose
{{PROJECT_PURPOSE — 2-3 sentences. What is being built and why.}}

## Domain knowledge
{{DOMAIN_CONTEXT — key facts agents need before touching any file.
Include: language/tech stack, key constraints, naming conventions,
any domain-specific rules that override general agent behaviour.}}

## File structure
{{KEY_PATHS — the 8-10 paths agents need to know. See AGENTS.md for full tree.}}

## Constraints — non-negotiable
{{HARD_CONSTRAINTS — rules that cannot be broken regardless of task.
Example for research: "status field is set only by human researcher."
Example for production: "never touch the payments module without approval."}}

## Commit discipline
Type: feat|fix|docs|test|refactor|perf|chore|ci|data|eval
Format: <type>(<scope>): <description>
Branch: task/<slug> — never push to main
PR: always open for human review
Changelog: auto-generated by commitizen on merge

## Agent team
PM → spec writing
Senior Dev → Python/JS implementation
Tester → pytest/jest suites and bug reports
Evaluator → metric interpretation and results
Research Analyst → literature and corpus extraction
Writer → documentation and paper prose
Skill Generator → new SKILL.md files from task patterns

## Human gates
{{List decisions that require human approval. Example:
- Setting status: primary on evaluation pairs
- Merging to main
- Publishing datasets or models}}

## Skill improvement signals
After any pipeline run, record:
- Did tester find BLOCKING issues? → which skill produced the bug?
- Did any spec miss an edge case? → update pm-spec skill
- Did any output need heavy revision? → update the producing skill
Report these to the Curator on its next cycle.
```

### pm-spec

```markdown
# PM Spec

Decompose a task into an unambiguous specification.

## When to use
Task contains: "build", "write", "implement", "create", "add feature"
OR orchestrator needs a spec before delegating to senior-dev.

## Instructions
1. Read the task. Identify inputs, outputs, logic, failure modes.
2. If SOUL.md or AGENTS.md exists in the repo, read them first.
3. Write the spec with these sections:
   TASK SUMMARY (one sentence, imperative mood)
   INPUTS (exact format, path, type)
   OUTPUTS (exact format, path, type)
   LOGIC (numbered steps, no ambiguity)
   EDGE CASES (every failure mode)
   LIBRARIES (explicit names — no vague "a parsing library")
   OUT OF SCOPE (explicit exclusions)
   ASSUMPTIONS (simplest interpretation of any ambiguity)
4. Do not write code. Output the spec only.
5. Commit discipline note: the spec itself is not committed.
   It is the input to senior-dev. Only code outputs are committed.

## Output format
Plain text spec. Section names in caps. No markdown headers.
No code blocks. Max 400 words. Clarity over completeness.
```

### senior-dev

```markdown
# Senior Dev

Write production-quality code from a PM spec.

## When to use
A PM spec exists for the current task.
Task contains: "code", "implement", "write the script", "build".
Never write code without a spec — request one from pm-spec first.

## Instructions
1. Read the PM spec completely before writing any code.
2. Read AGENTS.md and SOUL.md for project conventions.
3. Follow the spec exactly. Note every assumption in IMPLEMENTATION NOTES.
4. Single file unless spec requires multiple.
5. Every function: docstring, type hints where the language supports it.
6. Handle all spec edge cases explicitly.
7. Logging: print() with [INFO] [WARN] [ERROR] — no frameworks.
8. Entry point: main() + if __name__ == "__main__" guard (Python).
9. End file with:
   # IMPLEMENTATION NOTES
   # [every assumption, every spec ambiguity resolved]
10. Do not write tests. Do not add features not in spec.

## Commit format
feat(<scope>): <what the script does>

Body: explain the key implementation decision if non-obvious.
Footer: Refs: #<issue-number>

## Output format
Complete script only. No prose before or after.
```

### tester

```markdown
# Tester

Write test suites and structured bug reports.

## When to use
Code has just been produced by senior-dev.
Task contains: "test", "write tests", "check", "review the code".

## Instructions
1. Read the script and the PM spec.
2. SECTION 1 — TEST SUITE:
   - Happy path, one test per edge case, unit test per transform function
   - Use synthetic fixtures — never real project data files
   - Mock all external calls (APIs, file reads, network)
   - Tests must run without the project data present
3. SECTION 2 — BUG REPORT:
   For each spec vs code mismatch:
     ISSUE [N]: [title]
     Spec says: [quote]
     Code does: [description]
     Severity: BLOCKING | MINOR
     Fix: [one sentence]
   If clean: "NO ISSUES FOUND."
4. State "BLOCKING ISSUES PRESENT" at top of Section 2 if any.
5. Do not fix code. Do not rewrite code.

## Commit format
test(<scope>): add test suite for <script name>

## Output format
SECTION 1 — TEST SUITE
[complete test file]

SECTION 2 — BUG REPORT
[issue list or "NO ISSUES FOUND."]
```

### evaluator

```markdown
# Evaluator

Interpret quantitative results for research papers.

## When to use
Evaluation scripts have produced result files.
Task contains: "interpret", "analyse results", "write results section".

## Instructions
1. Read all result files before writing anything.
2. Address per the project's defined hypotheses (from SOUL.md).
3. Write two paragraphs:
   P1: factual results only — numbers, conditions, CIs, counts.
   P2: interpretation — hypotheses met or not, implications.
4. If a hypothesis is not met, say so directly.
5. Cite confidence intervals. Do not overstate precision.
6. Language: plain prose, academic register. No hedging beyond
   what the statistics warrant. No AI-marker language.

## Output format
Two paragraphs. Suitable for insertion into a short paper results
section. No headers. No bullet points.
```

### research-analyst

```markdown
# Research Analyst

Extract structured data from literature and corpora.

## When to use
Task involves: reading papers, extracting examples, mining a corpus,
sourcing examples or pairs from named academic references.

## Instructions
1. Work only from named sources. Never invent citations.
2. Flag uncertainty in a notes field — do not omit uncertain items.
3. Distinguish between: verified (human confirmed), unverified
   (candidate for review), disputed (conflicts with other source).
4. Never promote status to "primary" or equivalent — human sets that.
5. Output structured data (CSV rows, JSON lines, table) not prose.
6. Note every transcription or transliteration judgment call.

## Output format
Structured data rows pasted into conversation.
No file creation — human adds to repo after review.
```

### writer

```markdown
# Writer

Produce documentation, READMEs, design decisions, paper prose.

## When to use
Task contains: "document", "write up", "README", "methods section",
"design decisions", "changelog entry".

## Instructions
1. Match register to deliverable:
   - README: technical, concise, researcher audience
   - Design doc: reasoning-forward, future readers need the why
   - Paper section: academic, plain, no marketing
2. Language rules (enforced):
   - No AI-marker phrases ("it is worth noting", "importantly")
   - No em dashes
   - No nominalisation where a verb works
   - No colon-heavy constructions
   - Prose uses full sentences — bullet points only in quickstart steps
3. Do not imply community work is complete if it is future work.
4. Do not cite unresolved publications.

## Commit format
docs(<scope>): <what was documented>

## Output format
Markdown for docs/ files. Plain paragraphs for paper sections.
```

### skill-generator

```markdown
# Skill Generator

Create new SKILL.md files for new roles or task patterns.

## When to use
A task type has appeared 2+ times and has no existing skill.
Watson says "create a skill for this".
A new role is needed (security reviewer, data engineer, etc.).

## Instructions
1. Read the task pattern from recent conversation history.
2. Identify: what triggers this skill, what it does, what it outputs.
3. Write a SKILL.md following the framework format:
   - Name (one noun phrase)
   - Description (one sentence)
   - When to use (trigger conditions)
   - Instructions (numbered, specific, no ambiguity)
   - Output format (exact structure)
   - Commit format (type and scope for this role's output)
4. Write the skill to ~/.hermes/skills/<name>/SKILL.md
5. Commit a snapshot to docs/skills/<name>/SKILL.md
6. Announce the new skill to Watson on Telegram.
7. Tell Watson: "Run 2-3 tasks with this skill before the Curator
   reviews it. It will improve after real use."

## Output format
Complete SKILL.md file. Nothing else.

## Commit format
chore(skills): add <skill-name> skill
```

## Part 5: OpenClaw fallback config

When Hermes is unavailable, the same team runs on OpenClaw. The
SOUL.md files above become SOUL.md files in the OpenClaw agent
workspace. The agent addressing changes from Hermes-internal
(Hermes routes via delegate_task) to explicit Telegram handles.

## Part 7: Skill Generator — usage and patterns

The Skill Generator role creates new skills from observed task patterns.
It is the self-extensibility mechanism of the framework.

### When to trigger it

Send to Hermes on Telegram:

```
I've been asking you to [describe the pattern] repeatedly.
Create a skill for this so you handle it consistently going forward.
```

Or after any task that took multiple correction rounds:

```
That took too many revisions. Create a skill that encodes what we
learned: [describe the key lessons]. Name it [skill-name].
```

### Skill Generator output structure

Every skill it produces follows this template:

```markdown
# <Skill Name>

<One sentence description.>

## When to use
<Trigger conditions — what user messages or task types activate this.>

## Instructions
<Numbered steps. Specific. No ambiguity. Include:
- What to read first (SOUL.md, AGENTS.md, relevant docs)
- What to produce
- What constraints apply
- What NOT to do>

## Output format
<Exact structure of the deliverable.>

## Commit format
<type>(<scope>): <description pattern for this role's outputs>

## Self-improvement signals
<What failure modes indicate this skill needs updating.
Example: "If tester finds BLOCKING issues in output, update
step 4 to add explicit handling for [pattern].">
```

### Skill versioning

Skills are versioned by the Curator. The repo snapshot in `docs/skills/`
carries a version header:

```markdown
<!-- Skill version: 1.3 | Last improved: 2026-05-01 | Uses: 14 -->
```

The Curator writes this header after each improvement cycle. It is
the audit trail for the framework's self-improvement over time.

## Part 8: Deploying this framework to a new project

### Step 1 — Copy and parameterise

```bash
# In your new project repo
cp path/to/this/framework/AGENTS.md.template AGENTS.md
cp path/to/this/framework/SOUL.md.template SOUL.md
cp path/to/this/framework/.cz.toml .
cp path/to/this/framework/.commitlintrc.json .
cp -r path/to/this/framework/.github .
```

Replace all placeholders:
- `{{PROJECT_NAME}}` → your project name
- `{{REPO_OWNER}}` → your GitHub username
- `{{REPO_NAME}}` → your repo name
- `{{RESEARCHER_NAME}}` → your name
- `{{DOMAIN_CONTEXT}}` → 5-10 sentences of key domain knowledge
- `{{PROJECT_PURPOSE}}` → 2-3 sentence project summary
- `{{HARD_CONSTRAINTS}}` → non-negotiable rules for this project
- `{{KEY_PATHS}}` → the 8-10 important file paths in this repo

### Step 2 — Bootstrap Hermes

Send this message to Hermes on Telegram (replace placeholders first):

```
Set up the agentic dev team for a new project.
Project name: {{PROJECT_NAME}}
Repo: github.com/{{REPO_OWNER}}/{{REPO_NAME}}

1. Read SOUL.md and AGENTS.md from the repo root.
2. Load all skill files from docs/skills/ if they exist.
3. Install commitizen: pip install commitizen
4. Set up the daily docs-sync cron at 8pm UTC.
5. Set up the weekly Curator run at 7pm UTC Sunday.
6. Write memory: this project uses the agentic-dev-team framework.
7. Confirm setup on Telegram with a summary.
```

### Step 3 — Run smoke test

```
Run a smoke test of the dev pipeline:
1. PM: spec a script that reads a text file and counts lines.
2. Senior Dev: implement from spec.
3. Tester: test suite and bug report.
4. Commit results to branch task/smoke-test and open PR.
```

### Step 4 — Parameterise skills

After smoke test passes, update the domain context in each SKILL.md:

```
Update the senior-dev skill with this project context:
[paste your project's domain specifics]
Commit the updated snapshot to docs/skills/senior-dev/SKILL.md.
```
